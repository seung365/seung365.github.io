## 1. 시작하며

쇼핑몰을 운영하다 보면 같은 상품이 두 번 등록되는 일이 생기는데요. 둘을 하나로 합치면 사라지는 쪽 주소 `/products/123`은 남는 쪽 `/products/456`으로 보내 줘야 합니다. 이미 검색 결과나 공유 링크로 퍼진 주소라 그냥 지울 수는 없으니까요.

어느 상품으로 합쳐졌는지는 상품을 조회해 봐야 알 수 있습니다. 그래서 Next.js App Router라면 보통 페이지 안에서 이렇게 처리하게 되죠.

```tsx
// app/products/[id]/page.tsx
const product = await fetchProduct(id)

if (product.mergedInto) {
  redirect(`/products/${product.mergedInto}`) // 영구 이동이니 301이겠지?
}
```

그런데 터미널에서 응답 헤더만 받아(`-I`) 리다이렉트를 끝까지 따라가 보면(`-L`) 이렇게 나옵니다.

```bash
$ curl -sIL https://shop.example.com/products/123
HTTP/2 307
location: /products/456

HTTP/2 200
```

상품은 영구히 합쳐졌는데 돌아온 건 임시를 뜻하는 307이었습니다..

그래서 이번 글에서는 이 차이가 왜 생기는지, 검색엔진에는 어떤 영향을 주는지 아래 순서로 정리해 보겠습니다.

1. 301·302·303·307·308은 뭐가 다를까
2. 검색엔진(Google, 네이버)은 각 코드를 어떻게 볼까
3. 리다이렉트는 누가 낼까

---

## 2. 301·302·303·307·308, 뭐가 다를까?

리다이렉트 코드는 두 가지 기준으로 나눠 볼 수 있습니다.

| 코드 | 영구/임시 | 다음 요청의 메서드 | 브라우저 기본 캐시 |
| --- | --- | --- | --- |
| 301 Moved Permanently | 영구 | POST가 GET으로 바뀔 수 있음 | 캐시함 |
| 302 Found | 임시 | POST가 GET으로 바뀔 수 있음 | 캐시 안 함 |
| 303 See Other | 임시 | 항상 GET | 캐시 안 함 |
| 307 Temporary Redirect | 임시 | 원래 메서드 유지 | 캐시 안 함 |
| 308 Permanent Redirect | 영구 | 원래 메서드 유지 | 캐시함 |

### 첫 번째 기준: 버릴 건지, 넘겨줄 건지

영구 리다이렉트는 원래 주소를 버리는 리다이렉트입니다. 이사를 가면서 전입신고를 하는 것과 비슷한데요. "이 주소는 이제 안 씁니다. 앞으로는 저 주소로 오세요"라는 뜻이라, 브라우저는 별도 지시가 없으면 이 응답을 캐시해 두고 다음부터는 서버에 묻지도 않고 바로 새 주소로 갑니다. 검색엔진도 새 주소로 갈아타고요.

임시 리다이렉트는 원래 주소를 그대로 두고 이번 요청만 넘겨주는 리다이렉트입니다. 문에 "잠깐 자리 비움, 옆 사무실로 오세요" 메모를 붙여 두는 쪽에 가깝습니다. 주소는 계속 살아 있으니 브라우저는 매번 서버에 다시 묻습니다.

로그인하지 않은 사용자를 `/my/orders`에서 로그인 페이지로 보내는 게 대표적인 예입니다. `/my/orders`는 버린 주소가 아니죠. 로그인한 사람에게는 멀쩡한 페이지입니다. 그래서 임시여야 합니다.

헷갈릴 땐 "원래 주소를 앞으로도 쓸 건가?"만 물어보면 됩니다. 점검 페이지처럼 지금은 모든 사람을 넘기더라도, 나중에 되돌릴 주소라면 임시입니다.

### 두 번째 기준: 메서드를 지키는지

그럼 301과 308, 302와 307은 뭐가 다를까요? 이 기준이 생긴 이유는 301과 302의 역사에 있습니다.

HTTP/1.0에서 302의 이름은 "Moved Temporarily"였고, 같은 메서드로 새 주소에 다시 요청하라는 뜻이었습니다. 그런데 당시 브라우저 대부분이 `POST /users` → 302 → `GET /people`처럼 메서드를 GET으로 바꿔서 따라갔고, 301에서도 같은 일이 생겼는데요. 이게 사실상 표준처럼 굳어지자 HTTP/1.1은 의도를 둘로 나눴습니다.

- 303 See Other: "결과는 저기서 GET으로 받아라". 폼을 제출한 뒤 결과 페이지로 보낼 때 씁니다.
- 307 Temporary Redirect: "같은 메서드로 저기에 다시 요청해라". 302가 원래 하려던 일입니다.

영구 쪽은 한참 뒤인 2015년에 308 Permanent Redirect가 추가되면서 같은 구분이 생겼습니다. 결국 301과 308, 302와 307은 영구/임시라는 뜻은 같고, 메서드를 지키느냐만 다릅니다.

일반적인 페이지 이동처럼 GET 요청만 오간다면 둘은 동작 차이가 없습니다. 차이는 POST나 PUT 요청이 리다이렉트될 때 드러나는데요. Next.js가 301·302 대신 308·307을 기본으로 쓰는 것도 이 때문입니다.

## 3. 검색엔진은 어떻게 볼까?

### Google

Google 검색 센터 문서는 리다이렉트를 영구와 임시로만 나눕니다.

| 방식 | Google의 분류 | 의미 |
| --- | --- | --- |
| 301, 308 | 영구 | 목적지를 정규(canonical) 주소로 보는 강한 신호 |
| 302, 303, 307 | 임시 | 리다이렉트는 따라가지만 목적지를 정규 주소 신호로 쓰지 않음. 원래 주소가 검색 결과에 남을 가능성이 높음 |
| `<meta http-equiv="refresh">` 0초 | 영구 | |
| `<meta http-equiv="refresh">` 1초 이상 | 임시 | |
| JavaScript `location` 이동 | 영구로 해석하지만 권장하지 않음 | 렌더링에 실패하면 리다이렉트를 못 볼 수 있음. 서버 리다이렉트나 meta refresh를 쓸 수 없을 때만 사용 |

Google 입장에서는 301과 308이 같고, 302와 307도 같습니다. SEO에서 중요한 건 숫자가 아니라 영구냐 임시냐인 거죠.

처음의 상품 통합 예시처럼 307을 쓰면, Google은 `/products/456`을 정규 주소로 삼으라는 신호로 받아들이지 않습니다. 검색 결과에는 사라진 `/products/123`이 계속 남을 수 있고, 옛 주소가 쌓아 둔 신호도 새 주소로 넘어가지 않습니다.

### 네이버

네이버 서치어드바이저의 "웹 페이지의 이동" 가이드는 이렇게 안내합니다.

- 사이트나 페이지 주소를 바꿨다면 301을 쓴다.
- 일시적인 장애나 잠시 페이지를 바꾸는 경우에는 302를 쓴다. 그래야 검색로봇이 원래 페이지 정보를 유지한다.
- JavaScript 리다이렉트는 자제한다. 검색로봇이 목적지를 파악하기 어렵고, 리다이렉트를 숨기는 스팸 문서로 오해받아 저평가될 수 있다.
- meta refresh는 인식하지만, 되도록 HTTP 리다이렉트를 쓴다.
- 연속 리다이렉트는 5회를 넘기지 않고, 중간 주소도 모두 수집할 수 있어야 한다.
- 리다이렉트 반영에는 시간이 걸리므로, 주소를 바꾼 뒤에도 옛 주소의 리다이렉트를 한동안 유지한다.

여기엔 308이 안 나와서 "네이버는 301만 써야 하나?" 싶었는데요. 같은 사이트의 "HTTP 규약" 가이드를 보면 308을 "301과 유사하지만 요청 방식이 유지된다"고 설명하면서 영구 이동으로 분류하고 있었습니다!

### 정리하면

두 검색엔진의 문서를 합치면 기준은 이렇게 정리됩니다.

- 주소가 바뀌었으면 영구(301 또는 308), 잠깐 넘겨주는 거라면 임시(302 또는 307).
- HTTP 리다이렉트를 쓴다. meta refresh는 차선, JavaScript는 최후의 수단.
- 리다이렉트 체인은 짧게, 중간 주소도 모두 크롤링할 수 있게.

### Search Console 숫자, 줄이면 되는 걸까?

Google Search Console의 페이지 색인 생성 보고서에는 "리디렉션이 포함된 페이지"라는 항목이 있습니다. 상품을 정리하다 보면 이 숫자가 수백, 수천 건씩 쌓여 있는 걸 보게 되는데, 자연스럽게 "이걸 줄여야겠다"는 생각이 듭니다.

그런데 Search Console 도움말을 보면 이 항목은 "다른 페이지로 리다이렉트되는 정규가 아닌 URL이라 색인되지 않는다"는 뜻이고, 오류가 아닙니다. 리다이렉트 종류도 구분하지 않습니다. 그래서 307을 308로 바꿔도 이 숫자는 바로 줄지 않습니다. 바꾼 뒤에도 그 주소들은 여전히 리다이렉트되니까요.

307을 308로 바꿔서 달라지는 건 Google이 어느 주소를 정규로 고르느냐입니다. 이건 URL 검사 도구로 리다이렉트되는 주소를 검사하고, "Google이 선택한 표준 URL"을 보면 확인할 수 있습니다.

숫자 자체를 줄이고 싶다면 리다이렉트할 필요가 없는 주소를 찾아야 합니다. 예를 들어 완전히 삭제한 상품까지 전부 홈으로 리다이렉트하고 있다면, 그 주소들이 모두 이 항목에 쌓입니다. 대신할 페이지가 없는 주소라면 리다이렉트하지 말고 404로 닫아 주는 게 맞습니다.

## 4. 리다이렉트는 누가 낼까?

사실 리다이렉트를 내는 곳은 페이지만이 아닙니다. 요즘 브라우저는 https로 먼저 접속하지만, 오래된 링크나 크롤러는 `http://`나 끝 슬래시를 단 주소로 들어오기도 하는데요. 그런 주소로 요청해 보면 리다이렉트가 세 번 일어나고, 세 번 모두 상태 코드가 다릅니다.

```bash
$ curl -sIL http://shop.example.com/products/123/
HTTP/1.1 301 Moved Permanently   # ① http → https
HTTP/2 308                        # ② /products/123/ → /products/123
HTTP/2 307                        # ③ /products/123 → /products/456
HTTP/2 200
```

(`#` 뒤는 설명을 위해 붙인 주석입니다.)

왜 한 번에 456으로 안 가고 세 번이나 튕길까요? 요청은 서버에 들어올 때 여러 단계를 차례로 거치는데요. 각 단계는 자기가 판단할 수 있는 리다이렉트면 바로 돌려보내고, 아니면 안쪽으로 넘깁니다.

```text
브라우저 → ① 로드밸런서 → ② Next.js 라우터 → ③ 페이지 컴포넌트
```

①은 http인 걸 보자마자 돌려보내고, ②는 끝 슬래시를 보자마자 돌려보내고, ③은 상품을 조회해 보고 나서야 돌려보냅니다. 그래서 세 번이 됩니다.

응답 헤더를 자세히 보면 실제로 세 리다이렉트가 서로 다른 단계에서 나왔다는 걸 확인할 수 있습니다. Google Cloud 외부 로드밸런서 뒤에 Cloud Run으로 Next.js를 띄운 구성을 예로 들어 보겠습니다.

```text
# ① http → https
HTTP/1.1 301 Moved Permanently
location: https://shop.example.com/products/123/
via: 1.1 google
                                   ← server 헤더도, 앱이 붙이는 헤더도 없음

# ② 끝 슬래시 제거
HTTP/2 308
location: /products/123
refresh: 0;url=/products/123       ← Next.js가 308에만 붙이는 헤더
server: Google Frontend
via: 1.1 google, 1.1 google        ← 한 홉 더 들어감

# ③ 통합된 상품으로
HTTP/2 307
location: /products/456
x-powered-by: Next.js
cache-control: private, no-cache, no-store, max-age=0, must-revalidate
```

요청은 `로드밸런서 → Cloud Run → Next.js 서버` 순서로 들어오고, 리다이렉트는 각각 다른 단계에서 응답하고 있었습니다.

### ① 로드밸런서: 301

`via` 헤더가 하나뿐이고 `server` 헤더가 없습니다. 요청이 앱까지 가지도 않고 로드밸런서가 문 앞에서 바로 돌려보냈다는 뜻인데요. HTTP 프런트엔드의 URL 맵에 HTTPS 리다이렉트를 설정해 두면 로드밸런서가 직접 301을 돌려줍니다.

- 아는 정보: 호스트, 스킴, 경로 패턴 정도
- 장점: 앱 서버를 깨우지 않아 가장 빠르고, 앱 배포와 상관없이 동작함
- 상태 코드: URL 맵의 `redirectResponseCode`로 301·302·303·307·308 중에서 고를 수 있음(기본값 301)
- 바꾸려면: 앱 코드가 아니라 인프라 설정을 바꿔야 함

### ② Next.js 라우터: 308

`next.config.js`의 `redirects()`와 `trailingSlash` 처리는 페이지를 렌더링하기 전에 Next.js 라우터에서 일어납니다. 단서는 `refresh: 0;url=...` 헤더인데요. Next.js 서버 코드를 열어 보면 "IE11이 308을 모르니 호환용으로 `Refresh` 헤더를 붙인다"는 분기가 있고, 308 응답에만 이 헤더를 붙입니다.

- 아는 정보: 경로, 쿼리, 헤더, 쿠키 (`has`/`missing` 조건)
- 상태 코드: `permanent: true`면 308, `false`면 307. 301이 꼭 필요하면 `statusCode`로 지정
- `Cache-Control`이 붙지 않음: 영구 리다이렉트라 브라우저가 알아서 캐시함

옛 이벤트 페이지 주소를 새 주소로 옮기는 것처럼, 경로 패턴만 보고 판단할 수 있는 리다이렉트는 여기에 두면 됩니다.

미들웨어(Next.js 16의 `proxy.ts`)도 이 계층에 가깝습니다. 페이지 렌더링 전에 실행되고, `NextResponse.redirect(url, status)`로 상태 코드를 직접 정합니다(기본값 307). 언어 prefix가 없는 주소를 `/ko/...`로 통일하는 것처럼 요청을 보고 판단해야 할 때 씁니다.

### ③ 페이지 렌더링: 307

`x-powered-by: Next.js`와 동적 페이지에 붙는 `Cache-Control: no-store`가 보입니다. 페이지 컴포넌트가 상품을 조회하고, 통합된 상품이라는 걸 확인한 뒤에야 `redirect()`를 호출했기 때문입니다.

- 아는 정보: 데이터 조회 결과까지 전부. 어느 상품으로 합쳐졌는지는 조회해 봐야 알 수 있어서, 이 리다이렉트는 여기서만 할 수 있음
- 대가: 리다이렉트 하나를 위해 API 호출과 서버 렌더링이 일어남
- 상태 코드: `redirect()`는 307, `permanentRedirect()`는 308. 둘 다 상태 코드를 인자로 받지 않으니 페이지 안에서는 301을 낼 수 없음
- 주의: 스트리밍이 이미 시작된 뒤 `redirect()`가 호출되면 HTTP 리다이렉트 대신 `<meta>` 태그로 이동함. 응답 상태는 이미 200으로 나간 뒤라서, 라우트에 `loading.tsx`를 붙이면 검색엔진이 보는 응답이 바뀔 수 있음

처음 코드에서 "301이겠지?" 했던 게 사실은 307이었던 이유가 바로 여기에 있었습니다. `redirect()`는 기본이 임시입니다.

### 계층별로 비교해 보면

| 계층 | 예시 | 판단 근거 | 기본 코드 | 앱 배포로 롤백 |
| --- | --- | --- | --- | --- |
| 로드밸런서 | http → https | 호스트·스킴·경로 | 301 | 불가 (인프라 변경) |
| Next.js 라우터 | `redirects()`, 끝 슬래시 | 경로·쿼리·헤더·쿠키 | 307/308 | 가능 |
| 미들웨어 (`proxy.ts`) | `/path` → `/ko/path` | 요청 전체 | 307 (지정 가능) | 가능 |
| 페이지·Route Handler | 상품 통합, 로그인 복귀 | 데이터 조회 결과 | 307 / `Response.redirect`는 302 | 가능 |
| 클라이언트 (`router.push`, `location`) | 화면 안 이동 | 클라이언트 상태 | 상태 코드 없음 | 가능 |

원칙은 리다이렉트를 판단할 수 있는 가장 바깥 계층에서 내는 것입니다. 바깥일수록 빠르고, 검색엔진에게도 깔끔한 HTTP 리다이렉트로 보입니다. 클라이언트 이동은 검색엔진 입장에서는 JavaScript 리다이렉트라서 SEO 목적으로는 쓰지 않습니다.

### 롤백하면 끝일까?

표에는 "앱 배포로 롤백 가능"이라고 적었지만, 영구 리다이렉트는 그렇게 깔끔하게 되돌려지지 않습니다. 서버에서 리다이렉트를 지워도, 이미 응답을 캐시한 브라우저는 서버에 다시 묻지 않거든요.

예를 들어 `/member/*`를 `/account/member/*`로 옮기면서 처음부터 308을 걸었다가 롤백했다고 해 보겠습니다. 캐시된 브라우저는 이제 존재하지 않는 `/account/member/*`로 계속 가서 404를 받게 됩니다. 그래서 경로 구조를 바꿀 땐 307로 먼저 배포하고, 안정된 뒤 308로 올리는 순서가 안전합니다.

## 5. 그래서 언제 뭘 써야 할까?

지금까지의 내용을 흔한 상황에 대입해 보면 이렇습니다.

| 상황 | 코드 | 이유 |
| --- | --- | --- |
| http → https | 301 또는 308 | 주소가 영구히 바뀜. 보통 로드밸런서가 처리 |
| 끝 슬래시 정리 | 308 | 주소 정규화. Next.js 기본 동작 |
| 중복 상품 통합 (옛 id → 새 id) | 308 (`permanentRedirect()`) | 옛 주소의 신호를 새 주소로 넘겨야 함 |
| 옛 이벤트 페이지 → 새 주소 | 308 (`permanent: true`) | 주소를 영구히 옮김 |
| 언어 prefix 통일 (`/path` → `/ko/path`) | 308 | 노출 주소를 하나로 통일 |
| 경로 구조 개편 직후 | 307 → 안정되면 308 | 롤백할 가능성이 있음 |
| 로그인 뒤 원래 화면으로 복귀 | 307 | 사용자마다 목적지가 다름 |
| 권한이 없을 때 다른 화면으로 | 307 | 상태에 따라 목적지가 다름 |
| 공유·초대 링크를 실제 화면으로 | 307 또는 302 | 링크마다 목적지가 다름 |
| 폼 제출 뒤 결과 화면으로 | 303 | 새로고침해도 POST가 다시 가지 않게 함 |
| 점검 중 안내 페이지로 | 302 또는 307 | 검색엔진이 원래 페이지 정보를 유지해야 함 |
| 대신할 페이지가 없는 삭제된 상품 | 리다이렉트하지 않고 404 | 홈으로 보내면 "리디렉션이 포함된 페이지"만 쌓임 |

처음의 상품 통합 예시라면 이렇게 고치면 됩니다.

```tsx
if (product.mergedInto) {
  permanentRedirect(`/products/${product.mergedInto}`) // 308
}
```

Google은 301과 308을 똑같이 다루고, 네이버도 308을 영구 이동으로 분류하니 굳이 301을 고집할 이유는 없습니다. 페이지 안에서 301을 내려면 리다이렉트를 미들웨어로 옮기고 거기서 상품 API를 불러야 하는데, 그만큼의 이득은 없다고 봤습니다.

주소에 상품명을 넣는 사이트(`/products/123/blue-sneakers`)라면, 이름 오타를 정규 주소로 고쳐 주는 리다이렉트도 같은 이유로 `permanentRedirect()`를 쓰면 됩니다.

## 6. 마치며..

리다이렉트는 숫자 하나 고르는 일이라고 생각했는데, 결국 "이 주소를 버릴 건지, 잠깐 넘겨줄 건지"를 정하는 일이었습니다. 그리고 그 결정을 어느 계층에서 내리느냐에 따라 쓸 수 있는 코드도 달라진다는 걸 알게 됐습니다.

리다이렉트를 넣을 때 아래만 확인해 보시면 됩니다.

- [ ] 목적지가 요청마다 달라지는가? 그렇다면 임시(307, 302)
- [ ] 주소 자체를 옮겼고 검색엔진에 새 주소를 알려야 하는가? 그렇다면 영구(308, 301)
- [ ] 영구라면 롤백할 가능성이 있는가? 있다면 307로 먼저 배포하고, 안정된 뒤 308로 올린다
- [ ] 리다이렉트를 판단할 수 있는 가장 바깥 계층에서 내고 있는가?
- [ ] 쓰는 API가 실제로 어떤 코드를 내는가? `redirect()`는 307이다
- [ ] 대신할 페이지가 없는 주소까지 리다이렉트하고 있지는 않은가?
- [ ] 배포 뒤 `curl -sIL`로 상태 코드, 체인 길이, `Cache-Control`을 확인했는가
