디자이너가 Figma에서 아이콘을 바꿨는데, 코드에는 아무 일도 일어나지 않는다면 어떻게 될까요? 누군가 알려주기 전까지 앱은 계속 옛날 아이콘을 씁니다. 저희 팀도 그랬어요. 아이콘과 이미지를 Figma에서 코드로 가져오는 스크립트는 있었지만, **"언제 돌릴지"는 사람의 기억에 의존**했거든요.

이 글에서는 이 문제를 GitHub Actions로 해결한 과정을 정리해요. 평일 아침마다 Figma와 코드의 차이(drift)를 자동으로 감지하고, 차이가 있으면 재생성 PR까지 자동으로 올라오는 파이프라인이에요. 만들면서 밟았던 GitHub Actions의 함정들도 함께 공유할게요.

## 전체 구조 한눈에 보기

지금 운영 중인 최종 형태는 **하나의 워크플로 파일**에 담긴 두 개의 체인이에요.

```
평일 07:00 KST (cron)
  ├─ 이미지 체인: drift 체크 → 차이 있으면 재생성 + PR 생성
  │                → PR 머지(main push) 시 CDN 업로드 (DEV→STG→PRD)
  └─ 아이콘 체인: drift 체크 → 차이 있으면 컴포넌트 재생성 + PR 생성
                   (아이콘은 git에 커밋되는 React 컴포넌트라 업로드 단계가 없어요)
```

핵심 설계는 **체크와 재생성의 분리**예요. 매일 아침 도는 건 가벼운 체크뿐이고, 무거운 다운로드·재생성은 실제로 차이가 있을 때만 돌아요. 그리고 배포(CDN 업로드)는 재생성보다도 더 뒤, PR이 머지되는 순간으로 미뤄요 — 이 결정이 왜 나왔는지는 뒤에서 다룰게요.

## drift 체크는 "이름만" 비교해요

처음에는 매일 전체 에셋을 다시 받아서 비교할까도 생각했어요. 하지만 수백 개의 PNG를 매일 다운로드하면 체크 한 번에 몇 분씩 걸려요.

그래서 Figma REST API로 **노드 트리를 한 번만 읽어서 에셋 이름 목록만** 가져오고, 코드에 커밋된 이름 목록 파일과 비교하도록 했어요. 이미지를 한 장도 받지 않으니 분 단위였던 작업이 초 단위로 줄어요. 추가·삭제·이름 변경 중 하나라도 감지되면 스크립트가 `exit 3`으로 종료하고, 워크플로가 이 종료 코드를 보고 재생성을 트리거해요.

```bash
# fetch 스크립트에 --check 모드를 추가했어요
pnpm exec tsx scripts/fetch-images.ts --check
# 변경 없음: exit 0 / drift 감지: exit 3 / 실제 에러: exit 1
```

여기서 한 가지 주의할 점이 있어요. **"drift"와 "에러"의 종료 코드를 반드시 구분**해야 해요. 예를 들어 Figma 토큰이 만료됐을 때 exit 3이 나가면, 파이프라인이 "변경이 있다"고 착각하고 재생성을 오발사해요. 그래서 API 실패는 exit 1로 죽도록 분리했어요.

## GitHub Actions에서 밟은 함정 3가지

### 1. cron은 main에 있는 워크플로만 돌아요

워크플로를 다 만들고 브랜치에 올린 뒤, 다음 날 아침에 확인해 보니 실행 이력이 비어 있었어요. 버그가 아니었어요. GitHub Actions의 `schedule`(cron)은 **기본 브랜치(main)에 있는 워크플로만 등록**해요. `workflow_dispatch` 수동 실행 버튼도 마찬가지고요.

즉, 스케줄 워크플로의 "전원 스위치"는 main 머지예요. 브랜치에서 아무리 완성해도 머지 전에는 켜지지 않아요. 참고로 GitHub cron은 정각에서 몇 분에서 십수 분까지 밀리는 게 흔하니, 정각 실행을 전제로 뭔가를 설계하면 안 돼요.

### 2. GITHUB_TOKEN이 만든 PR은 CI가 안 돌아요

재생성 워크플로가 PR을 자동으로 만드는데, 이 PR에 CI가 하나도 붙지 않았어요. GitHub은 무한 루프를 막으려고 **기본 `GITHUB_TOKEN`으로 만든 PR이나 dispatch에서는 후속 워크플로를 실행하지 않아요.**

봇이 만든 PR에도 CI를 돌리려면 별도 토큰이 필요해요. 처음에는 대상 저장소 하나로 범위를 좁힌 fine-grained PAT(Contents·Pull Requests write)를 저장소 secret으로 등록해서 해결했어요. 그런데 PAT는 만료 기한이 최대 1년이라, "1년 뒤 누군가 갱신해야 한다"는 사람 의존이 남아요.

그래서 지금은 **GitHub App 토큰으로 전환**했어요. 조직에 봇용 App을 설치하고 워크플로에서 `actions/create-github-app-token`으로 실행할 때마다 단기 토큰을 발급받아요. 개인 계정에 묶이지 않고, 만료 갱신 일정도 사라져요. 봇이 PR을 만드는 파이프라인을 오래 운영할 거라면 처음부터 App 토큰을 권해요.

### 3. repository_dispatch는 inputs를 못 받아요

처음 버전에서는 체크 워크플로와 재생성 워크플로가 별도 파일이었고, 체크가 재생성을 부를 때 `repository_dispatch` 이벤트를 썼어요. 그런데 이 이벤트는 `workflow_dispatch`의 `inputs`를 전달하지 못해요. 값을 넘기려면 `client_payload`를 쓰고, 받는 쪽에서 `github.event.client_payload`로 읽어야 해요. 워크플로 두 개가 이벤트로 통신하니 "누가 무엇을 넘겼는지"가 파일 두 개에 흩어지고, 조건 분기도 이벤트 종류마다 달라져서 점점 읽기 어려워졌어요.

그래서 결국 **두 워크플로를 한 파일로 합쳐서 dispatch 자체를 없앴어요.** drift 체크 job이 종료 코드를 output으로 내보내고, 재생성 job이 `needs`로 그 값을 조건 삼아 돌아요.

```yaml
regen_img:
  needs: drift_img
  if: ${{ !cancelled() && (수동 실행 || needs.drift_img.outputs.code == '3') }}
```

이벤트로 통신하던 것을 job 의존성으로 바꾸니 값 전달 제약이 사라지고, 파이프라인 전체가 한 파일에서 읽혀요. 워크플로 간 `repository_dispatch` 통신을 설계하고 있다면, 먼저 "이게 정말 별도 워크플로여야 하는가"부터 물어보세요.

## 승인 게이트, 넣었다가 뺐어요

프로덕션 CDN에 자동으로 에셋이 올라가는 게 불안해서, 처음에는 안전장치를 겹겹이 쌓았어요. 자동 경로는 개발 환경까지만 반영하고, 운영 반영은 수동 체크박스로만. 나중에는 GitHub Environment의 **수동 승인 게이트**까지 붙여서, 업로드 job이 승인자의 클릭을 기다리게 했죠.

그런데 운영해 보니 이 게이트가 문제를 막는 게 아니라 만들고 있었어요.

- **승인이 이미 있는 확인과 중복이었어요.** 이름이 바뀌어 PR이 생기는 경로는 PR 리뷰·머지가 이미 사람 확인이에요. 수동 실행 경로는 버튼을 누른 사람이 이미 확인자고요. 게이트는 같은 사람에게 같은 질문을 두 번 하는 장치였어요.
- **승인을 깜빡하면 더 나쁜 상태가 돼요.** 코드(생성 타입)는 머지됐는데 승인이 안 눌려 PNG가 CDN에 없으면, 앱에서 이미지 404가 나요. 실제로 한 번 겪었어요. "안전장치"의 실패 모드가 사람 기억에 의존하고 있었던 거예요.
- 승인 대기 중인 job이 concurrency lock을 쥐고 있어서 **후속 실행이 데드락**에 걸리는 문제도 두 번 고쳤어요.

그래서 게이트를 제거하고 트리거를 재배치했어요. **PR 머지가 곧 배포 승인**이에요 — 재생성 PR이 main에 머지되면 그 push가 업로드를 트리거하고, DEV→STG→PRD 순서로 반영돼요. rsync가 멱등이라 중간에 실패해도 재실행하면 이미 반영된 환경은 건너뛰고 이어가요. 스케줄 실행은 여전히 PR 생성까지만 하고 업로드하지 않아요.

배운 것은 이거예요. **안전장치를 추가하기 전에, 그 확인을 이미 누가 하고 있는지 먼저 세어보세요.** 중복 확인은 안전을 더하지 않고 새로운 실패 모드(깜빡함, 데드락)만 더해요.

## 생성 코드의 diff 노이즈 잡기

자동 PR이 올라오기 시작하니 새로운 문제가 보였어요. 실제 변경이 없는데도 생성된 타입 파일에 diff가 생기는 거예요. 원인은 **생성기의 raw 출력과 prettier 포맷의 불일치**였어요. 로컬에서는 커밋 훅이 prettier를 돌리지만, CI의 재생성 경로는 훅을 건너뛰어서 포맷이 어긋난 파일이 커밋되고 있었죠.

해결은 생성기가 파일을 쓰기 전에 직접 prettier를 통과시키는 거예요.

```ts
import { format } from 'prettier'

async function writeFormatted(filePath: string, content: string) {
  const formatted = await format(content, { ...prettierConfig, filepath: filePath })
  fs.writeFileSync(filePath, formatted)
}
```

코드를 생성하는 스크립트를 만든다면, "포맷터는 누가 언제 돌리는가"를 생성기 안에서 끝내는 게 마음이 편해요. 훅이나 CI 설정에 의존하면 경로마다 결과가 달라져요.

## 보너스: 아이콘 PR에 미리보기 붙이기

자동 PR의 마지막 불편함은 리뷰였어요. 아이콘은 React 컴포넌트(`.tsx`)로 커밋되는데, GitHub PR은 정적 이미지 파일만 렌더링해 주니까 리뷰어는 SVG path 문자열의 텍스트 diff만 봐야 했어요. `d="M12 2L4.5 20.29..."`를 읽고 아이콘 모양을 상상할 수 있는 사람은 없죠.

그래서 재생성 시점에 Figma Images API로 **해당 아이콘의 PNG 렌더 URL을 받아 PR 코멘트에 박아 넣었어요.** 추가·변경·제거된 아이콘을 분류해서 표로 보여주고, 코멘트는 마커 주석으로 upsert해서 PR당 하나만 유지해요.

재미있는 점은 이 PNG URL이 Figma가 그때그때 렌더해서 자기 S3에 올려주는 **약 30일짜리 임시 URL**이라는 거예요. 그런데도 괜찮아요. GitHub이 코멘트를 처음 렌더링할 때 이미지를 camo 프록시로 캐시하기 때문에, 원본 URL이 만료된 뒤에도 코멘트에서는 계속 보여요. 저장소에 SVG나 PNG를 상주시키지 않고도 시각적 리뷰가 가능해져요.

한 가지 한계는 있어요. 코멘트의 PNG는 Figma 원본 그대로지만, 실제 배포되는 컴포넌트는 색상 치환(`#000` → `currentColor`)과 svgo 최적화를 거쳐요. 그러니 이 미리보기가 보장하는 건 "디자이너가 그린 모습"까지이고, "변환 후 앱에서 렌더링되는 모습"은 아니에요. 저희는 여기까지면 충분하다고 판단했어요.

## 마치며

완성된 파이프라인을 요약하면 이래요.

- **평일 아침** cron이 Figma와 코드의 에셋 이름을 비교해요 (이름만, 초 단위)
- **차이가 있으면** 재생성이 자동으로 돌고, 미리보기 코멘트가 달린 PR이 올라와요
- **PR을 머지하면** 그게 곧 배포 승인이에요 — DEV→STG→PRD CDN까지 자동으로 반영돼요

디자이너는 Figma에서 작업하던 대로 작업하고, 개발자는 아침에 올라온 PR의 미리보기를 보고 머지 버튼만 누르면 돼요. 실제로 지금은 봇이 만든 재생성 PR이 매주 여러 건씩 머지되면서 파이프라인이 일상이 됐고, 새 Figma 프레임을 자동화에 태우는 일도 노드 ID 한 줄을 배열에 추가하는 PR로 끝나요. "아이콘 바뀐 거 반영해 주세요"라는 메시지가 사라진 것이 가장 큰 수확이에요.

비슷한 파이프라인을 만든다면 이 세 가지만 기억하세요. **스케줄 워크플로는 main에 머지해야 켜진다. 봇 PR에 CI를 돌리려면 App 토큰(또는 PAT)이 필요하다. 안전장치를 추가하기 전에 그 확인을 이미 누가 하고 있는지 세어본다.**
