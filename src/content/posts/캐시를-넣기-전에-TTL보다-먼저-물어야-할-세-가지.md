지난 몇 달 동안 캐시 때문에 생긴 문제를 여러 번 만났어요. 매거진을 고쳤는데 화면에 반영이 안 되고, 이미지를 바꿨는데 일부 사용자는 옛 이미지를 보고, 같은 조회 실패가 에러 모니터링에 두 번씩 쌓였어요.

캐시를 붙일 때마다 처음 떠올린 질문은 "몇 초로 할까"였어요. 그런데 돌아보면 문제가 난 곳은 숫자가 아니었어요. 숫자를 정하기 전에 답했어야 할 질문 세 가지를 건너뛴 곳이었어요.

1. 이 캐시는 누구와 공유되나
2. 틀린 값이 들어갔을 때 누가, 언제 비울 수 있나
3. 캐시에 무엇이 저장되나

이 글은 식품 검색 **웹**(Next.js App Router)과 앱 **웹뷰**를 운영하며 겪은 사례로, 세 질문을 하나씩 정리한 거예요.

## 캐시는 생각보다 여러 층에 있다

"캐시를 건다"고 말할 때 가리키는 층이 사람마다 달라요. 저희 서비스에서 실제로 쓰는 층만 꼽아도 다섯 개예요.

| 층 | 위치 | 공유 범위 | 비우는 방법 |
| --- | --- | --- | --- |
| React `cache` | 서버 | 요청 한 번 | 요청이 끝나면 사라짐 |
| Next.js 데이터 캐시(`fetch`의 `next.revalidate`) | 서버 인스턴스 | 모든 사용자 | 시간 만료, `revalidateTag`·`updateTag` |
| TanStack Query | 브라우저 탭 메모리 | 사용자 한 명, 탭 하나 | `invalidateQueries`, 새로고침 |
| 브라우저 HTTP 캐시 | 사용자 기기 | 사용자 한 명 | 서버가 비울 수 없음 |
| CDN | 엣지 서버 | 모든 사용자 | 무효화 API |

표의 오른쪽 두 열이 이 글의 첫 번째, 두 번째 질문이에요. 같은 "60초 캐시"라도 어느 층에 거느냐에 따라 의미가 완전히 달라져요.

## 1. 누구와 공유되나

### 매거진 수정이 반영되지 않았다

운영 담당자가 매거진 글을 고쳤는데 화면이 그대로라는 제보가 왔어요. 처음에는 백엔드 에디터 문제로 의심했는데, 따라가 보니 프론트가 매거진 응답을 최대 1시간 캐시하고 있었어요. 상수 하나가 세 곳에서 쓰이고 있었어요.

| 위치 | 층 |
| --- | --- |
| 매거진 상세 `fetch` | Next.js 데이터 캐시 |
| 매거진 목록 `fetch` | Next.js 데이터 캐시 |
| 목록 클라이언트 컴포넌트의 `staleTime` | TanStack Query |

앞의 두 곳은 서버에 있고 모든 사용자가 공유하는 캐시예요. 그래서 누군가 한 번 캐시를 채우면, 원본이 바뀌어도 1시간 동안 모든 방문자가 옛 글을 받아요. 글을 고친 운영자도 예외가 아니에요.

1시간이라는 값을 정할 때 저는 "매거진은 자주 안 바뀌니까"라고 생각했어요. 읽는 사람 입장에서는 맞는 말이에요. 하지만 고친 사람 입장에서는 "방금 고쳤는데 왜 안 바뀌지?"가 돼요. 공유 캐시의 TTL은 결국 "데이터가 바뀐 뒤 모두에게 얼마나 늦게 보여도 되나"를 정하는 값이고, 그 늦음을 가장 먼저 겪는 사람은 데이터를 바꾼 사람이에요. 상수를 60초로 줄였고, 세 곳이 같은 상수를 쓰고 있어서 한 줄로 끝났어요.

다만 지금 돌아보면 아쉬운 해법이에요. 독자는 하루 늦게 봐도 괜찮고, 글을 고친 사람은 바로 보고 싶어요. 서로 다른 두 요구를 숫자 하나로 타협한 게 60초예요. 그마저도 즉시 반영은 아니에요. `revalidate`는 만료 뒤 첫 요청에 옛 값을 먼저 주고 뒤에서 갱신하니, 고친 직후에는 여전히 옛 글이 보일 수 있어요. 서버 캐시 시간과 클라이언트의 `staleTime`이 같은 상수에 묶여 있는 것도 따로 정해야 할 값을 하나로 합쳐 둔 셈이에요.

문제는 "누구와 공유되나"가 아니라 다음 절의 "누가 비울 수 있나"에 있었어요. 독자를 위해 TTL은 길게 두고, 글이 수정될 때만 그 글의 캐시를 비우는 게 맞는 답이에요. 매거진은 백엔드 에디터에서 수정되니 백엔드가 발행 시점에 Next.js 서버를 불러 줘야 하는데, 그 작업까지 가지 않고 숫자를 줄이는 쪽을 골랐어요. 지금은 매거진 트래픽이 적어서 60초로도 비용이 거의 없고 이후 불만도 없어서 그대로 두고 있어요.

### 공유되는 캐시에는 모두에게 같은 값만

공유 범위를 먼저 생각하면 넣으면 안 되는 데이터도 보여요. 식품 상세 페이지에 로그인 회원에게만 보이는 정보를 붙일 때, 서버 HTML은 항상 비회원 기준으로 그리고 회원 데이터는 클라이언트에서 덧씌웠어요. 서버 데이터 캐시는 A 사용자가 채운 값을 B 사용자도 받기 때문에, 사용자마다 다른 값이 들어가는 순간 다른 사람의 데이터가 보일 수 있어요.

## 2. 누가, 언제 비울 수 있나

### 브라우저 캐시는 원격으로 비울 수 없다

디자인 시스템 이미지는 `img_100_gym.png` 같은 고정 이름으로 CDN에서 서빙해요. 이미지를 바꾸면 같은 이름으로 덮어쓰고, 배포 스크립트가 바뀐 경로만 골라 CDN 캐시를 무효화해요.

그런데 동료가 리뷰에서 이렇게 물었어요. "CDN TTL과 브라우저 TTL이 둘 다 1년인데, 의도한 건가요?"

CDN 무효화는 엣지 서버에 있는 사본을 지우는 일이에요. 사용자 브라우저에 이미 들어간 사본은 건드리지 못해요. 브라우저는 URL을 키로 캐시하고, `max-age`가 남아 있는 동안은 서버에 요청 자체를 보내지 않아요. 그러니 브라우저 TTL이 1년이면, 이미지를 한 번 받은 사용자는 CDN을 아무리 비워도 최대 1년 동안 옛 이미지를 볼 수 있어요.

이미 받아 간 캐시를 지울 방법을 하나씩 따져 봤어요.

| 방법 | 결과 |
| --- | --- |
| 앱 재배포 | 남는다. JS는 새로 받아도 그 안의 이미지 URL이 같다 |
| 이미지 재업로드 + CDN 무효화 | 남는다. CDN만 새 파일을 갖는다 |
| CDN 콘솔에서 브라우저 TTL 변경 | 남는다. 앞으로 받는 응답에만 적용된다 |
| `Clear-Site-Data` 헤더 | 쓰기 어렵다. 캐시된 이미지는 요청을 보내지 않아 헤더를 받을 기회가 없다 |
| URL 변경(파일명 해시, `?v=`) | 새로 받는다 |

확실한 방법은 URL을 바꾸는 것뿐이었어요. 동료의 지적이 맞았어요.

같은 1년 TTL인데 문제가 없는 곳도 있었어요. 일본 서비스의 매거진 이미지는 업로드할 때마다 해시가 붙은 새 이름을 받아요. 내용이 바뀌면 URL도 바뀌니, 브라우저가 1년을 들고 있어도 옛 이미지를 볼 일이 없어요. Next.js 빌드 결과물에 `max-age=31536000, immutable`을 붙일 수 있는 것도 같은 이유예요. 파일 이름에 콘텐츠 해시(파일 내용으로 계산한 해시)가 들어가 있어서, 내용이 바뀌면 이름도 바뀌거든요.

그래서 두 번째 질문은 이렇게 다시 쓸 수 있어요. 비울 수 있는 층은 길게 둬도 되고, 비울 수 없는 층은 짧게 두거나 URL을 바꿀 수 있을 때만 길게 둔다.

방향을 반대로 잡아도 함정이 있어요. CDN은 길게, 브라우저는 짧게 두면 CDN이 붙여 보내는 `Age` 헤더 때문에 브라우저 캐시가 받자마자 만료될 수 있어요. 브라우저는 `max-age - Age`로 남은 신선도를 계산하거든요. CDN에 3일 머문 사본이라면 `Age`가 3일이라, 브라우저 `max-age`가 1시간일 때는 받자마자 이미 만료된 상태예요.

### 너무 자주 비워지는 것도 문제다

비울 수 없어서 생기는 문제와 반대로, 원하지 않을 때 비워지는 문제도 있었어요. 큰 로띠 JSON을 컴포넌트에서 `import`하면 JS 청크 안에 들어가요. 청크 파일 이름에도 콘텐츠 해시가 붙어서, 같은 청크의 코드가 한 줄만 바뀌어도 이름이 바뀌어요. 로띠는 그대로인데 사용자는 로띠까지 통째로 다시 받아요.

그래서 로띠를 번들에서 빼서 배포와 상관없는 고정 URL로 CDN에 올렸어요. 그런데 고정 URL이 되는 순간, 앞에서 본 고정 이름 이미지의 문제가 그대로 돌아와요. 로띠도 이미지와 같은 방식으로 바뀐 파일만 CDN을 무효화하고 있어요.

해시 이름은 비우기 쉽지만 너무 자주 비워지고, 고정 이름은 오래 남지만 비우기 어려워요. 어느 쪽이 낫다기보다, 이 파일이 "다른 코드와 함께 바뀌는지, 혼자 바뀌는지"에 따라 고르는 문제였어요.

### 직접 비우도록 하자

식품 상세 페이지의 비회원용 후기 미리보기는 서버 데이터 캐시에 60초 동안 들어가요. 그런데 후기를 쓰거나 지워도 미리보기가 늦게 바뀌었어요. 브라우저가 API 서버에 직접 쓰기·삭제를 요청해서, 캐시를 관리하는 Next.js 서버에는 변경 사실이 전달되지 않았거든요.

그래서 후기 조회 `fetch`에 태그를 달고, 쓰기·삭제에 성공하면 클라이언트가 Server Action을 불러 해당 태그의 캐시를 비우게 했어요.

```ts
// 조회: 식품별 태그를 단다
await getGuestReviews(id, {
  next: { revalidate: 60, tags: [`food-reviews:${id}`] },
})

// 쓰기 성공 뒤 클라이언트가 부르는 Server Action
'use server'
export async function expireGuestReviews({ id }: { id: string }) {
  updateTag(`food-reviews:${id}`)
}
```

Next.js 16의 `updateTag`는 Server Action에서만 부를 수 있고, 태그를 즉시 만료시켜요. 비슷한 `revalidateTag`는 다음 요청에 이전 값을 먼저 주고 뒤에서 갱신해요. 방금 쓴 후기가 바로 보여야 해서 `updateTag`를 골랐어요.

매거진 때와 같은 문제였지만, 이번에는 TTL을 줄이는 대신 데이터가 바뀐 직후 캐시를 만료시키도록 했어요. 후기 쓰기·삭제는 브라우저에서 요청하니, 성공 직후 Server Action을 호출하는 처리를 프론트에서 추가할 수 있었기 때문이에요.

여기에도 아직 남은 질문이 있어요. `output: 'standalone'`의 기본 설정에서 데이터 캐시는 서버 인스턴스마다 로컬 파일로 따로 있어요. 태그를 비우면 그 요청을 받은 인스턴스의 캐시만 지워져요. 지금은 인스턴스가 한 대라 괜찮지만, 여러 대로 늘리는 순간 "누가 비울 수 있나"의 답이 "요청을 받은 인스턴스 하나만"으로 바뀌어요. 그때는 인스턴스끼리 공유하는 cache handler가 필요해요.

## 3. 무엇이 저장되나

### 응답을 공유하는 것과 결과를 공유하는 것

식품 상세 페이지에서는 `generateMetadata`와 페이지 컴포넌트가 같은 혈당 상태 조회를 각각 불러요. 둘은 서로 값을 넘길 수 없어요.

Next.js에는 한 요청 안에서 같은 URL·옵션의 `fetch`를 한 번만 보내는 요청 메모이제이션이 있어요. 그래서 처음에는 React `cache`가 왜 필요한지 의문이었어요. API 호출은 어차피 한 번만 나가니까요.

차이는 실패할 때 드러나요. 요청 메모이제이션이 공유하는 건 `fetch`의 응답이에요. 응답을 받은 뒤 상태 코드를 판정하고, 실패를 잡아 에러 모니터링에 보고하는 코드는 호출한 곳마다 따로 돌아요. 그래서 API가 503을 돌려주면 같은 실패가 두 번 보고돼요.

```ts
export const fetchFoodGlucoseState = cache(async (id: string) => {
  const glucose = await getGlucoseReaction(id, { next: { revalidate: 60 } }).catch((error) => {
    reportError(error) // cache가 없으면 호출한 곳마다 한 번씩 보고된다
    return null
  })
  return toGlucoseState(glucose)
})
```

React `cache`는 함수의 결과를 통째로 공유해요. 조회, 판정, 실패 보고까지 한 번만 돌고, 두 번째 호출은 첫 번째의 결과(`null`)를 그대로 받아요. 둘 다 "한 번만 조회한다"고 설명할 수 있지만, 저장하는 대상이 다르니 막아 주는 것도 달라요.

`cache`는 인자를 참조로 비교해요. 객체를 넘기면 호출마다 새 키가 되니, 원시값인 `id` 문자열을 받도록 했어요.

### HTML은 캐시하지 않고 데이터만 캐시한다

같은 질문을 페이지 단위에 질문하면, 식품 검색 웹은 렌더링 결과(HTML·RSC payload)를 캐시하지 않고 데이터만 캐시해요. 루트 레이아웃이 요청 쿠키를 읽어서 모든 라우트가 동적 렌더링되기 때문이에요.

```tsx
export default async function RootLayout({ children }) {
  // 첫 화면부터 회원/비회원을 맞게 그리기 위해 요청 쿠키로 세션을 판정한다
  const cookieStore = await cookies()
  // ...
}
```

첫 화면부터 헤더의 로그인 상태가 깜빡이지 않게 하려고 일부러 고른 구조예요. 대신 페이지 전체를 정적으로 서빙할 기회를 내줬어요.

둘 다 가져갈 방법으로 Next.js 16의 Cache Components(Partial Prerendering)를 검토했어요. 페이지 뼈대는 빌드 때 만들어 두고, 쿠키가 필요한 헤더 프로필 영역만 `Suspense` 안에서 요청 때 채우는 방식이에요. 다만 앱 전체 설정이라 켜는 순간 `Suspense` 밖에서 `cookies()`나 캐시되지 않은 `fetch`를 쓰는 곳마다 경고가 뜨고, 그걸 전부 정리해야 해요. 아직 적용하지는 않았고, 정적 서빙이 정말 필요해지는 시점에 다시 볼 생각이에요.

## 마치며

처음에는 캐시를 성능을 위한 기능으로 생각했어요. 사례를 모아 보니 캐시는 "이 데이터가 얼마 동안, 누구에게 틀려도 되는가"에 대한 약속에 더 가까웠어요. TTL은 그 약속의 한 숫자일 뿐이에요. 그 틀림을 누구와 나누는지, 틀렸을 때 누가 고칠 수 있는지, 무엇을 틀린 채로 들고 있는지가 함께 정해져야 약속이 지켜져요. 다음에 캐시를 붙일 때는 숫자보다 이 세 가지를 먼저 적어 두려고 해요.
